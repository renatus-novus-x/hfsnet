# ICMP / ping.x 調査メモ（2026-11-18、書き込み障害中の読み取り調査）

## 実測結果（2026-11-18 夜、XEiJ + トレース版ドライバ + ホストダンプで確定）

### 落ちていた本当の理由は SOCK_RAW ではなかった

- トレース版ドライバ（全 TI 呼び出しを HFSTRACE.BIN に記録）で観測すると、ping.x は socket() に到達する前に **TI_get_MIB（関数番号23、引数0）だけを呼んで落ちていた**。hfsnet は未実装関数として -1 を返し、ping.x はその戻り値をポインタとして参照して SIGBUS。
- 対処: joynetd（yunkya2）の実装と同じく、{NULL, 0, "IP"} / "ICMP" / "UDP" / "TCP" の4要素のダミー MIB 配列へのポインタを返すよう guest/hfsnet.c に TI_get_MIB を実装。これで ping.x は先へ進むようになった。**この修正は GUI と無関係に本体側の互換性向上**（従来「ICMP が必要なため対象外」としていた ping.x の起動不可の主因は、実は MIB 未実装だった）。
- その後の呼び出し列（実測）: socket(0, 2, 1) = PF_INET / SOCK_RAW / IPPROTO_ICMP → sendto（64バイト）→ socklen のポーリング多数 → close。受信は socklen が正になったら recvfrom に来る形。

### 送信パケット形式（確定）

- ゲストが OP_SEND で渡すのは **ICMP のみ（IP ヘッダーなし）**、64バイト固定（-c 3 127.0.0.1 の実測）:
  - 種別8（エコー要求）、コード0、チェックサム、識別子 **0x0080**、シーケンス 0,1,2,...
  - データ部56バイト: 先頭4バイト = clock_t の送信時刻（約1/100秒単位で増加）、残りは 04 05 06 ... という位置由来のパターン埋め（BSD ping.c の作法どおり。man の「clock_t 構造体 + パディング」と一致）
- 宛先は sendto の sockaddr で渡される（ファイルプロトコルの addr/port 欄）。connect は使わない。

### 受信側の未検証点と環境制約

- 応答の組み立て（ICMP のみ、識別子・シーケンス・データをゲストのものに差し替え）は実装済みだが、**この VM のサンドボックスではホスト側 ICMP が一切打てない**ため実応答での受信確認は未了:
  - ping ソケット生成 = EACCES（net.ipv4.ping_group_range が 65534 65534 で自グループを含まず、CAP_NET_RAW も bounding set から外れている）
  - raw ソケット生成 = EPERM（seccomp 系。無接続 sendto の EPERM と同種の制約）
  - つまり VM 内では「3送信・0受信」が上限。受信経路の実証は通常ホスト（Windows の IcmpSendEcho / 通常の Linux・macOS）で行う必要がある。macOS の Actions ランナー上でファイルプロトコル経由の raw 送受信テストを行う案が有力（ゲスト実機は不要な部分の検証になる）。

### ping.x のもう1つの前提: 浮動小数点演算パッケージ

- 送受信が進んでも、統計表示（平均値などの浮動小数点演算）で「演算パッケージが未登録です」のダイアログが出て止まる環境がある。
- 原因は hfsnet ではなく Human68k 側の構成: 標準の CONFIG.SYS にある `DEVICE = \SYS\FLOAT2.X`（浮動小数点演算パッケージ for X680x0、IEEE フォーマット）が読み込まれていない最小構成だったため。
- 検証環境では HFS ルートに CONFIG.SYS（同行）と SYS\FLOAT2.X（シャープ無償公開 Human68k 3.02 システムディスクから抽出）を置き、起動時に「浮動小数点演算パッケージ for X680x0 version 2.03」が登録されることを確認済み。

## ping.x の素性

- 実体は BSD ping の移植。バイナリ内の文字列: `$Id: ping.c,v 1.7 1994/08/09 04:10:49 Niggle Exp $`、オプション文字列 `c:i:n`（man の -c / -i / -n と一致）、"TCP/IP driver"、"ICMP"。
- 現行 hfsnet では起動直後に SIGBUS で落ちる（compat-check/RESULTS.md に記録）。socket() の -1 を検査していないため。裏を返すと、SOCK_RAW を受理すれば先へ進むはず。

## マニュアル（TCPPACKA man/ping.8）の記述

- 送る ECHO_REQUEST データグラムは「IP ヘッダー + ICMP ヘッダー + clock_t 構造体 + パディング」で構成される、とある。これはワイヤ上の形の説明で、アプリがドライバへ渡す形と同一とは限らない。

## 形式の仮説（要実測）

- 本家 BSD ping.c の作法: 送信は ICMP 部分だけを組み立てて raw ソケットへ渡し（IP ヘッダーはスタックが付ける）、受信は IP ヘッダー付きで受け取り、先頭の IP ヘッダー長ぶんをずらして ICMP を読む。識別子は自プロセスの pid 由来、シーケンスと送信時刻（RTT 計算用）をデータ部に埋める。
- inetd.x の raw ソケットがこの BSD 方式かどうかは未確認。hfsnet のファイルプロトコル自体が観測路になるので、確定は実測で行う:
  1. ゲストが SOCK_RAW を受理するよう変更（ti_socket）。
  2. ホスト側に raw スロットのダンプ機能を付け、XEiJ で ping.x を実行。
  3. OP_SEND のペイロード（IP ヘッダーの有無、宛先の渡し方）と、ping.x が受け取りに来る形（RECV の長さ要求、STATE の使い方）を観測して確定する。

## ホスト代理の設計メモ

- 送信: ペイロードから宛先 IP と ICMP（種別8、識別子、シーケンス、データ）を取り出し、platform.h の icmp_echo() で実際に打つ。
- 受信: 応答をゲストの識別子・シーケンス・データで組み立て直す。ゲストが IP ヘッダー付きを期待するなら、送信元＝ping 先、宛先＝ゲスト側のアドレス（ホストのローカルエンドポイント）で IP ヘッダーを付けて返す。
- RTT はゲストが自前で測る（送信時刻をデータに埋める方式）ため、ホストは時刻を改変しない。ファイルポーリングの遅延は RTT に上乗せされる。
