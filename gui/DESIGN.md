# hfsnet ホスト側 GUI 版 設計ドキュメント

2026-11-18 初版。元の hfsnet チャットで提示した設計提案に、このチャットでの決定を反映したもの。

## 前提（変えないもの）

- ファイルプロトコル（HFSREQ.BIN / HFSRES.BIN、ビッグエンディアン）は無変更。
- ゲスト側 hfsnet.x は原則として無変更。ただし ICMP 対応（後述）に必要な SOCK_RAW の受理だけは例外として手を入れる。
- Python 版 hfsnethost.py はリファレンス実装として残す。既存の test/sim_test.py と test/udp_test.py を、C++ エンジンの回帰テストとして使う。

## 決定事項

### セッションは単一（2026-11-18 ユーザー決定）

共有フォルダは1つだけを対象とし、複数フォルダの同時監視は行わない。

見送りの理由:

- 想定される用途は「複数のエミュレータを同時に通信させる」ケースだが、現在の検証の進め方では必要になっていない。
- hfsnet のゲストは固有の IP アドレスを持たず、ホストの実ソケットを借りて通信する。同一ホストで複数セッションを動かすと:
  - 外向き接続だけなら、ホスト OS が接続ごとに別ポートを割り当てるため技術的には共存できる。
  - 待ち受け（bind / listen）は同じポートを複数セッションで掴めず競合する（iperf サーバ同士など）。
  - LAN から見ると全ゲストが同じホスト IP になり区別できない。ゲスト同士の通信も、相手が同じ IP になってしまい素直にはできない。
- 将来どうしても2環境を同時に使いたくなったら、そのフォルダ向けに Python 版ホストを別途起動する現行の方法で足りる。

## 構成

- ホストエンジンを C++ 化し、GUI と同一プロセスに組み込む。
- エンジンは GUI 非依存のクラスとしてワーカースレッドで動かす。ポーリング間隔は Python 版と同じ約10ms。
- GUI はスレッドセーフなスナップショットを描画する。

## 技術選定

- GLFW + GLEW + Dear ImGui の OpenGL3 バックエンド。グラフは ImDrawList で描き、カスタム GL コードはほぼなし。
- フォルダ選択ダイアログは nativefiledialog-extended。
- ビルドは CMake、依存は vendoring。
- ソケットは Winsock2 と BSD ソケットの差を薄い層で吸収する。
- 対象は Windows / macOS / Ubuntu。

## 画面設計

- フォルダパスの欄に「参照」「開始・停止」。
- TX / RX の累計、現在のレート、60秒の折れ線グラフ。
- ソケット表（Phase 2）。
- ログペイン。

## 監視の仕様

- 数えるのはペイロードのバイト数だけ（SEND で実際に送れた分、RECV でゲストへ渡した分。プロトコルヘッダは含めない）。
- レートは1秒差分でグラフと共有する。
- STATE のポーリングは行ログに出さず、回数として数える（Python 版は全操作を印字するため、sntp 検証で約1,900行のポーリング行が出た実績がある）。

## プラットフォーム注意点

- Windows: HFSRES.BIN の差し替えは一時名→リネームをリトライし、ダメなら直接上書きにフォールバックする（Python 版の対策を再現）。
- Windows: 日本語フォルダ名のためにワイド文字パスを使う。
- macOS: OpenGL は非推奨だが 4.1 まで使える。GL_SILENCE_DEPRECATION と vendoring した GLEW で対応する。
- ファイル通知 API は使わず、ポーリングを維持する。

## 第一目標：ICMP 対応で ping.x を動かす（2026-11-18 ユーザー指示）

プロトタイプの第一目標は、ICMP をサポートして ping.x が応答を受け取れるようにすること。

現状: ping.x は SOCK_RAW を使うが、現行ドライバの ti_socket は SOCK_RAW に -1 を返すため動かない（仕様として未対応にしてきた）。

必要な変更:

- ゲスト側: ti_socket で SOCK_RAW を受理し、スロットに raw 種別を持たせる。OP_OPEN の引数で種別をホストへ伝える（UDP で使っている既存の仕組みの流用）。プロトコル形式自体は変えず、ソケット種別の値が1つ増えるだけ。
- ホスト側（C++ エンジン）: ゲストから受けた ICMP エコー要求（タイプ8）から識別子・シーケンス・データを取り出し、platform.h の icmp_echo() で実際にエコーを打つ。応答が返ったら、ゲストの識別子・シーケンス・データでエコー応答（タイプ0）を組み立て、チェックサムを再計算してゲストへ返す。
- ICMP は C++ エンジンの機能とし、Python 版ホストは従来どおり（ICMP なし）をプロトタイプの範囲とする。

調査事項:

- ping.x が送る／受け取るパケットの形式（IP ヘッダの有無、チェックサムの扱い、宛先の渡し方）を、実物と libsocket の逆アセンブルで確認する。
- macOS の ping ソケットが特権なしで使えるかを実測する。

## プラットフォーム抽象：platform.h（2026-11-18 ユーザー指示）

本体コードは3プラットフォームを意識せずに書けるよう、プラットフォーム依存部を platform.h の裏に逃がす。機種依存コードは3プラットフォーム分を個別に書いてよい。

platform.h の裏に隠すもの:

- ソケットの初期化・終了、生成、非ブロッキング化、送受信、エラーコードの正規化。
- ICMP エコー（icmp_echo()）。実装は OS ごとに異なる（次節）。
- 応答ファイルの差し替え（一時名→リネームのリトライと直接上書きフォールバック）。
- パスの表現（Windows のワイド文字変換）。
- 高精度時刻。

本体（エンジンと GUI）は platform.h だけを見て書き、#ifdef を散らさない。実装ファイルは platform_win.cpp / platform_mac.cpp / platform_linux.cpp のように分ける。

### ICMP エコーのプラットフォーム別実装

- Windows: IcmpSendEcho（iphlpapi）。管理者権限は不要で、OS の ping 機能をそのまま使う。
- Linux: ping ソケット（SOCK_DGRAM + IPPROTO_ICMP）。net.ipv4.ping_group_range の設定に依存する。カーネルが識別子を書き換えるため、応答の組み立て時にゲストの識別子へ戻す。
- macOS: ping ソケット（SOCK_DGRAM + IPPROTO_ICMP）を第一候補とし、プロトタイプで実測する。
- 生の raw ソケットは管理者権限が要るため、どの OS でも使わない。

## ファイル選択ダイアログの見た目

nativefiledialog-extended のダイアログは OS 標準の見た目になるため、ダークな ImGui ウィンドウとは揃わない。ただし開いているのは数秒のモーダル操作で、多くの ImGui 製アプリでも普通のやり方。利点は、操作に迷わないこと、日本語パス・ネットワークドライブ・最近使ったフォルダを OS が正しく扱うこと。代替案の ImGui 内蔵ブラウザは見た目は揃うが、操作性と正確さで劣る。画面イメージは仕様スライドに含めた。

## フェーズ分け

- Phase 1（プロトタイプ）: エンジン移植 + platform.h + 単一セッション + フォルダ選択 + 開始・停止 + トラフィック／グラフ + ログ + ICMP 対応（ping.x 実動まで）。
- Phase 2: ソケット表（エンジン側に相手アドレスとスロット別カウンタの保持が要る）+ 設定保存。
- Phase 3: トレイ常駐、ドラッグ＆ドロップ。

## プラットフォーム別のビルドと確認（2026-11-18 ユーザー指示）

- Windows: Visual Studio でビルドが通る構成にする。VM 内では VS 互換コンパイラでビルドし、Wine 上で動作確認する。
- macOS: GitHub Actions で自動ビルドし、その結果を監視する方向で動作確認する。ランナー上では GUI の実動はできないため、ビルド成功に加えて、ヘッドレスモードのエンジンに対して sim_test.py / udp_test.py を回すところまでを CI の確認範囲とする。
- Linux: VM 内で直接ビルドし、XEiJ 上の ping.x 実動まで確認する。

注意: renatus-novus-x の gh トークンには workflow スコープが無いため、`.github/workflows/` 以下の push はトークン経由では弾かれる。ワークフローファイルの登録は GitHub の Web エディタ経由（iperf で実績あり）か、ユーザーのスコープ付与が必要。
